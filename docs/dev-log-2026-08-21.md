# Lewad Dev Log — 2026-08-21

## Summary

Lewad V1 is beyond the original core flows: it now has secure member flows,
separated admin/super-admin spaces, recharge and request-to-service workflows,
DB4 business submissions, maps, install UX, focused tests, and CI. This log
records the implementation and deployment guardrails future work must retain.

### Admin / Super Admin

- `/admin` is the operational admin space; `/super-admin` is the dedicated
  super-admin space. Defaults and redirects keep admins in `/admin` and
  super-admins in `/super-admin`; users cannot access either space.
- Super-admin admin-management, contextual profile/settings routes, and
  role-specific mobile bottom navigation are present.

### Profile / Settings

- Settings include language, theme, text size, and password-reset email. The
  full language selector is in settings; the navbar quick toggle is FR/AR.
- Profile updates are partial: absent optional values preserve existing data.
- Avatar upload uses the `avatars` bucket, JPEG/PNG only, with a 2 MB limit.
  The image uploads before its profile reference is saved.

### Recharge / Credits

- `/recharge` creates a pending `recharge_requests` record by RPC and opens
  WhatsApp only after the request exists.
- Offers are fixed server-side. Admins approve/reject stored pending requests
  only; there is no arbitrary credit-creation path.
- React never mutates `wallets` or `credit_ledger` directly.

### DB4 Business Submissions

- `20260821000002_db4_business_submissions.sql` supplies
  `business_submissions`, `create_business_submission`, and admin
  list/detail/approve/reject RPCs.
- Each submission has a server-owned fixed amount of 500 MRO. Approval creates
  an approved, verified establishment and active main branch; decisions write
  audit events.
- The base DB4 migration (`20260821000002`) was applied remotely and its
  migration-history record repaired after verification.

### Maps

- `20260821000003_db4_maps_location_support.sql` is the DB4 map-support
  migration. Its remote application is not confirmed, so it remains documented
  as local/unapplied.
- Add-business uses map-only selection. Normal users do not see latitude or
  longitude inputs; coordinates remain component state and move through the
  typed RPC payload. Location and nearest place remain optional.
- Search results show nearest place and expose View on map/Directions when
  coordinates exist. Missing coordinates use localized fallback copy.
  Directions use an external Google Maps URL without an API key or SDK.
- Leaflet is lazy-loaded. The service worker does not cache map tiles.

### PWA / Install UX

- Manifest, icons, and a production-only service worker exist.
- Install guidance and a popup exist without App Store/Play Store claims.
  `beforeinstallprompt` is conditional; iOS remains Share → Add to Home Screen.

  `directionsUrl()` builds an external Google Maps URL — no API key, no SDK.
- **The add-business map picker exists:**
  `src/components/map/MapLocationPicker.tsx`, lazily imported by the submission
  form. Tap-to-place, an explicit "use current location" button, and a
  "place marker here" action that selects the current map centre (also the

  `VITE_MAP_TILE_URL`, defaulting to public OpenStreetMap.

  in component state and travel only through the typed RPC payload. Do not
  reintroduce a manual-coordinate fallback for normal users.
- **Manual QA is still needed for the full user → admin → search map flow.**
  Nothing recorded here replaces an end-to-end pass against the deployed schema.

Known gap, not a regression: the admin submission detail modal shows owner,
business, contact, status, and amount, but no location, nearest place,
coordinates, or mini map. The admin location block described in the maps UX plan
remains outstanding admin-UX polish.
