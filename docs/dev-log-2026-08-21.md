### Client History (`/history`) — later on 2026-08-21

- **`/history` is a member-facing activity list**, reachable from the mobile
  drawer, the account menu, the desktop bar at `xl`, a button in the `/profile`
  header, and a "Where did my points go?" link on `/credits`. It stays out of
  the four bottom tabs, which remain `search · credits · recharge · profile`.
- **No migration was needed and none was written.** `search_logs`,
  `credit_ledger`, `recharge_requests` and `business_submissions` already carry
  owner-scoped `select` RLS policies and grant only `select` to
  `authenticated`. The browser therefore reads its own rows and nothing else —
  the server enforces that, not `src/lib/userHistory.ts`. Adding a
  `SECURITY DEFINER` history RPC would have widened the surface for no gain and
  would have left the page dead until an owner applied it.
- **`src/lib/userHistory.ts` is read-only** and contains no `insert`, `update`,
  `upsert`, `delete` or `rpc` call. It reads the most recent N rows from each of
  the four sources, merges them by date, and returns the newest N. Taking the
  top N of each source guarantees the merged top N is exact.
- **A paid search is counted once.** A debited search writes both a
  `search_logs` row and a `search_debit` ledger row at the same instant, so the
  ledger query excludes `search_debit` and the search event carries its own
  cost. Without that the member would appear to have spent two points per
  search.
- **Suggestions never appear as activity**, because autocomplete writes nothing
  at all — there is no row for the history to find. A contract test pins the
  inverse so a future change cannot start charging keystrokes to the timeline.
- **The submission period degrades gracefully.** `period_months` only exists
  after `20260821000004`; PostgREST rejects a whole query that names a missing
  column, so the loader tries the full select and falls back to the guaranteed
  columns. An unapplied migration hides the duration instead of emptying the
  section.
- **The copy carries no internal vocabulary.** A test asserts the `history`
  block of all three dictionaries contains none of RPC, RLS, `search_logs`,
  `credit_ledger`, `recharge_requests`, `business_submissions`, ledger, UUID,
  schema, backend or policy. Record ids are React keys only and are never shown.
- An admin or super admin opening `/history` sees their own events and only
  their own, which is the permitted "own account context" — the same rule that
  already governs `/profile` and `/credits`.

### Contact, Pricing, Suggestions and Arabic Search — later on 2026-08-21

- **Official contact details** are `42015464` for phone and WhatsApp and
  `lewad.help@gmail.com` for email. They live only in `contact` in
  `src/lib/content.ts`; the landing, footer, `/contact`, the recharge WhatsApp
  handoff and the submission WhatsApp handoff all read that object. The
  WhatsApp deep link carries the Mauritanian country code
  (`https://wa.me/22242015464`). Never recopy a number into a component.
- **Business submissions now cost 200 MRO for 3 months.**
  `20260821000004_update_business_submission_amount_200_mro.sql` sets the
  server constants, adds `period_months`, and returns the period from the
  creation, list and detail RPCs. The retired 500 MRO value survives only in
  `check (amount_mro in (200, 500))` so historical rows keep the amount their
  owner was quoted. `businessSubmissionOffer` in `src/lib/content.ts` is
  display-only for the pre-submission form block and is pinned to the
  migration by a contract test.
- **Search suggestions are real.** `suggest_services`
  (`20260821000005_search_suggestions_and_arabic_support.sql`) is read-only:
  it debits nothing, writes no `search_logs` row, and returns no phone,
  WhatsApp, website or description — contact details stay behind the paid
  search. It is authenticated-only, bounded to 1–80 characters and 8 rows,
  and escapes wildcards. The browser debounces 220 ms and aborts stale
  requests. Clicking a suggestion only fills the input; the user still runs
  the search, so no point is ever spent without an explicit action.
- **Arabic search works.** `establishments.name_ar` had existed since
  `20260820000000` and is written on every approval, but
  `search_services_with_credit` never matched against it, so an Arabic query
  could only ever hit a Latin name. The same migration adds
  `normalize_arabic_search` — it strips harakat, superscript alef and
  tatweel, folds أ إ آ ٱ to ا, ى to ي and ة to ه, lower-cases and collapses
  whitespace — and applies it to both sides of every comparison in the paid
  search and in suggestions. Every credit, rate-limit, escaping and result
  bound from the superseded function is preserved verbatim and pinned by
  `tests/searchSuggestionsContracts.test.ts`.
- **The "did you mean" proposal no longer comes from demo data.** It used
  `searchDemoEstablishments`, so accepting it spent a point chasing a name
  that does not exist in the directory. It now probes `suggest_services` and
  proposes nothing when there is no real close match. `searchDemoEstablishments`
  is left in place but has no remaining consumer.
- Migrations `20260821000004` and `20260821000005` are **local and unapplied**.
  Until they are applied, `/add-business` submission fails and Arabic search
  and suggestions return nothing. Order matters: `20260821000003` must be
  applied before `20260821000004`.
